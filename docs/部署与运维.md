# 部署、备份恢复、删除与回滚

对应验收文档 §11（安全、部署与运维验收）与 §14（交付清单）。

---

## 1. 运行形态

| 进程 | 命令 | 说明 |
|---|---|---|
| API | `uvicorn app.main:app --host 0.0.0.0 --port 8000` | 无状态，可多副本 |
| Worker | `python -m app.worker` | 消费 `jobs` 表；多副本安全（乐观锁领取） |
| Web | `npm run start`（3000） | Next.js |
| PostgreSQL | 托管或容器 | 生产数据库 |
| Redis | 仅 `queue_backend=celery` 时需要 | 否则可不部署 |
| 对象存储 | 本地卷或私有 S3 | 原片与关键帧一律私有 |

**API 与 Worker 必须分进程**；Worker 不监听端口，不对外暴露。

## 2. 首次部署（干净环境）

```bash
git clone <repo> && cd Learning_aigc
cp .env.example .env
# 至少修改：CJX_SECRET_KEY（随机 32+ 字节）、数据库口令、CJX_ENV=prod
# 生产请设置 CJX_ALLOW_SELF_REGISTRATION=false

# 依赖安装（锁定版本）
python -m venv .venv
.venv/bin/pip install -r backend/requirements.txt

# 数据库迁移 + 内容初始化
cd backend
export PYTHONPATH=.
../.venv/bin/alembic upgrade head
../.venv/bin/python -m app.cli seed          # 同步知识卡片 + 创建首批账号（按需）

# 环境自检（必须输出 ffmpeg/ffprobe 为 true）
../.venv/bin/python -m app.cli doctor

# 启动
../.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port 8000 &
../.venv/bin/python -m app.worker &
```

Docker 方式：

```bash
export CJX_SECRET_KEY=$(openssl rand -base64 32)
export POSTGRES_PASSWORD=$(openssl rand -base64 24)
docker compose up -d --build
docker compose exec api python -m app.cli seed
curl -fsS http://127.0.0.1:8000/api/v1/healthz
```

反向代理示例见 `deploy/nginx.conf.example`（HTTPS + `client_max_body_size 110m`）。
**对外只暴露反代**，API/Worker/数据库/存储都不直接暴露。

## 3. 健康检查与就绪

| 端点 | 用途 | 判定 |
|---|---|---|
| `GET /api/v1/healthz` | 存活探针 | `status=ok` 要求数据库可达且 ffmpeg/ffprobe 存在；含 `worker_backlog` |
| `GET /api/v1/readyz` | 就绪探针 | 知识卡片数量、provider、队列后端 |

`worker_backlog` 持续增长说明 Worker 未消费，应告警。
Worker 心跳超时（默认 600 秒）后任务会被重新排队或标记 `worker_lost` 失败，不会永久停在处理中。

## 4. 配置与环境变量

全部配置以 `CJX_` 前缀注入，见 `.env.example`。**密钥类变量不得写入日志与导出**：
日志过滤器已对 `token=`、`api_key`、`authorization`、`password` 做脱敏，但不要主动打印配置对象。

## 5. 备份与恢复

- **数据库**：`pg_dump -Fc chai_jing > backup.dump`，建议每日 + 上线前手动一次；保留 7 天（§11）。
- **对象存储**：`backend/var/storage`（本地）用卷快照；S3 用生命周期与版本控制。
- **知识卡片**：`backend/knowledge/cards.yaml` 在版本控制中，随代码一起备份。

恢复流程（**必须先应用删除记录**）：

```bash
# 1) 恢复数据库
pg_restore -c -d chai_jing backup.dump
# 2) 重新应用删除标记：把备份里已删除、但恢复后"复活"的项目再次软删除
python - <<'PY'
from app.db import session_scope
from app.models import Project, CleanupTask, utcnow
# 依据删除审计（deleted_at 非空记录）或删除清单文件重建删除标记与清理任务
PY
# 3) 恢复对象存储快照
# 4) 跑健康检查与 3 个项目的对象引用核对
```

**恢复演练要求**（文档 §11）：恢复到测试实例，核对至少 3 个项目的原片与关键帧可读；
本仓库提供流程但**尚未演练**，属 M5 待完成项。

## 6. 删除与数据清理

`DELETE /projects/{id}` 的行为：

1. 立即写入 `deleted_at`，应用内所有读取自此返回 404（不等待物理删除）；
2. 该项目的 `queued`/`running` 任务被标记 `cancel_requested` + `deleted_marker`；
3. 每个素材写入一条 `cleanup_tasks`；
4. `cleanup_project` 任务被 Worker 消费，删除对象存储中的原片与派生对象（关键帧/分析归档/导出）。

Worker 在写库前会再次检查删除标记（`project.deleted_at`），因此**任务不会把结果写回已删除项目**。
若清理失败，`cleanup_tasks.attempts` 累加，达到 5 次标记 `failed` 需人工介入。

## 7. 升级与回滚

```bash
# 升级
git fetch --tags && git checkout vX.Y.Z
.venv/bin/pip install -r backend/requirements.txt
cd backend && alembic upgrade head
# 重启 API 与 Worker（先 Worker 后 API 或滚动）

# 回滚
alembic downgrade -1          # 如涉及不兼容迁移
git checkout vX.Y.{Z-1}
# 重启；若数据已不可逆变更，按第 5 节从备份恢复
```

发布前打标签：`git tag -a v0.1.0 -m "M5 发布"`，验收报告记录 commit 与配置摘要。

## 8. 运维常见问题

| 现象 | 排查 |
|---|---|
| 任务长期 `queued` | Worker 未启动或已退出：查看 `/healthz.worker_backlog`，重启 Worker |
| 任务 `worker_lost` | 任务超过最大重试；检查 Worker 日志与内存，手动 `POST /jobs/{id}/retry` |
| 上传 413 | 超过 100MB 上限（`CJX_MAX_UPLOAD_BYTES`） |
| 上传 415 | 编码不是 H.264、容器不在白名单、或文件损坏/伪装扩展名 |
| 分析结果为 unknown 景别 | 正常：`multimodal_provider=offline` 时不做语义判断；配置真实模型后恢复 |
| 外部模型 401/400 | 直接失败不重试（设计如此）；检查密钥与模型 ID |
| 429/超时 | 自动重试 2 次（指数退避）；仍失败则任务 `failed` 并写明原因 |
| 单镜头失败 | 任务仍 `succeeded` 但 `partial=true`，该镜头 unknowns 说明原因 |
